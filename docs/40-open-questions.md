(b) The `strict` tier (all terms) applies to **every** file under `packages/db/schema/**`, `packages/db/migrations/**` (and any `*.sql`), `packages/db/seed/**`, `packages/print/**`, plus any path with a segment matching `anc*`, `antenatal*`, `pregnan*`, `obstet*`, `usg*`, `ultrasound*`, `sonograph*`, `scan*`, `form-f*`/`form_f*`, `mtp*`, `labour*`, `prompts/`, `*.prompt.*`. Generic patient-demographic Hindi labels (`लिंग`) belong in i18n (key-scoped), not hard-coded in strict-scope files. The Form F `living_children[].sex` key allowlist stays. | D-6 | Upper bound on money/rate inputs | Two layers. (a) **Policy cap** in `setting` key `money.max_rate_paise`, default **₹10,00,000** (`100000000` paise) per unit rate / single amount entry; zod input schemas and tRPC procedures reject values above it with a clear i18n error. (b) **Hard DB ceiling**: every rate/amount `bigint` column gets an additive CHECK `<= 1000000000000` paise (₹1,000 crore per row) so qty × rate and SUM() can never overflow bigint. `MAX_PAISE` in `packages/shared` drops to `Number.MAX_SAFE_INTEGER`-aligned safe value. UI shows a confirm prompt when a rate is ≥10× the previous rate for that service (typo guard). | Issue #27 |
| D-7 | Backdated / corrected service rates | `effective_from` must be **today or later** (Asia/Kolkata). Same-day corrections require a user-supplied reason (no canned reason). Both are audited. Already-posted bill lines are never re-priced; they keep their stored rate. | Issue #42 |
| D-8 | Room-specific vs room-agnostic rate precedence | Take the newest row on or before the date. Ties go to the room-specific row. | D-10 | Runtime forbidden-term guard on inputs | Server-side zod refinement with `findForbiddenTerms` on **every** free-text input: USG procedure code/name, all masters names, all patient free-text (referred_by, occupation, address, override reasons), and all clinical notes. Rejections return an i18n error and are logged to `access_log` without the text itself (rule 15). Guarding general free text too is the safest choice under rule 7 ("no free-text hint"). | Issue #37 |
| D-11 | Allowed characters in patient names | Server-side zod (shared schema, also used by the form) allows only Unicode letters and combining marks (so Devanagari matras/halant work), spaces, apostrophe `'`, hyphen `-` and dot `.`; 1–60 chars after trim, whitespace collapsed. Hindi transliteration suggestion is not offered for rejected input. Output stays escaped as now. | Issue #56 |
| D-12 | Age "0" at registration | A bare `0` is **rejected** with the message "For a newborn type age in days, e.g. 0d or 3d" (bilingual); `patients.create` is not called. | D-13 | Gaps in the forbidden-term patterns (sentence phrasings, Hindi/Hinglish variants) | Widen the **strict** tier in `packages/shared/src/compliance/forbidden-terms.ts` (shared by runtime and CI): (a) a fetus/baby/unborn/garbh/bhrun subject followed within a few words by is/will be/hoga/hogi + any gendered word (boy/girl/male/female/son/daughter and Hindi/Hinglish forms); (b) genitalia or chromosome (XY/XX) wording near a fetal subject; (c) Hindi `जेंडर`/`सेक्स`/`लिंग` near `भ्रूण`/`गर्भ`/`बच्चा`/`बच्चे`; (d) plural/oblique Hindi forms (लड़के, लड़कियां, लड़कियाँ, बेटे, बेटियां, छोरा, छोरी) and double-vowel / alternate transliterations (ladkaa, ladkii, ladkiya, ladakaa, ladki). | D-14 | Refund / credit-note approval when a cancellation is split | Supervisor-PIN thresholds are **cumulative per bill**: approval is required when (credits already issued on the bill + this credit) exceeds `cancelApprovalAbovePaise`, or when (refunds already paid on the bill + this refund) exceeds `refundApprovalAbovePaise`. The day-close report lists every bill with more than one credit note on that day. Same approach as `applyDiscount`. | Issue #70 |

| D-17 | Login / PIN lockout abuse | Throttle failures by **(username, source IP)**: 5 failures from one IP lock that pair for 15 min (doubling, max 4 h), without blocking the same user from other IPs. Separately, a per-IP limit of 20 failures in 15 min across all usernames blocks that IP. A username-wide lock is applied only after 20 failures from ≥3 distinct IPs in 1 h, and it **never applies to owner role holders** (they keep the pair/IP throttles). Owner recovery is out-of-band: server CLI `pnpm --filter @hmis/db admin:unlock <username>` (also callable through `docker compose exec worker`), which clears locks and is audited. Supervisor-PIN failures use their own counter (per user+session) and never lock password login. Lockouts and unlocks write `access_log` without the password. | Issue #96 |
| D-18 | Raw data kept by patient import | At staging, scan **headers and every cell** with `findForbiddenTerms` (strict tier on headers, always tier on cells). Store **only mapped columns** in `import_row.raw`; unmapped columns are dropped before persisting, and `import_batch.headers` keeps only the mapped headers. Once a batch is committed or cancelled, `raw` is nulled (make the column nullable additively) and the error report then comes from the stored error codes only. Staged batches never committed are purged by a worker job after **7 days**. Batch-level create/commit/cancel/purge events are audited (row-level stays excluded from the audit trigger). | Issue #95 |
| D-19 | Which earlier visit gives follow-up entitlement | Only a consultation that was **actually billed and settled** counts as the base visit: its consultation charge is on a bill with status `final` and no amount due (or fully covered by a package/payer). Unpaid draft OPD visits are **not** auto-cancelled. The day-close report lists them as "Unpaid draft visits" so the cashier can collect the fee or cancel the visit with a reason. Regression test: previewVisit with one unpaid draft encounter for (patient, doctor) returns `followUp.eligible = false`; once that bill is paid it returns `true`. | Issue #111 |
| D-20 | WhatsApp duplicate sends after an ambiguous provider failure | Patient messages are **at most once**: a missed reminder is acceptable, a duplicate is not, since receipts are also printed. A timeout, abort or connection reset after the request body was sent makes the attempt `unknown`, and it is **not** resent automatically. A claim stranded in `sending` past CLAIM_TIMEOUT_MS also becomes `unknown`, not requeued. Pass the outbox id as `biz_opaque_callback_data` so a later status webhook (if configured) can mark it sent. `unknown` messages show on the admin messaging screen with a manual "Resend" (needs `admin.settings.manage`, audited).
